# macOS / Apple Silicon — what the demo actually costs

Machine: MacBook, Apple Silicon, 16 GB, macOS 26.5. Docker Desktop VM 7.7 GB.
Everything below runs the container path (`RUNNER=docker`, `lotusim:focus-v2`
under Rosetta), rebaked 2026-07-30. Unity 2023.1.20f1 / HDRP 15.0.7.

Method for every row: `./scripts/run_regatta.sh 400 smoke`, wall time measured
around the whole run, `sim t` taken from the gate's own output. The **wall time
for one lap** is the headline number, because it is what "slow to watch" means —
it folds the clock rate and the length of the lap into the one figure a person
experiences. RTF is reported alongside so the two can be told apart.

## The simulation is already at real time

| config | verdict | wall / lap | sim | marks | RTF |
|---|---|---|---|---|---|
| **baseline** (comm `0.01`, xdyn `--dt 0.005`, wind `3.0`) | SMOKE PASS | **274 s** | 242.9 s | 2/2 | 0.89 |
| comm step `0.02` | SMOKE PASS | 261 s | 242.4 s | 2/2 | 0.93 |
| wind `4.5 m/s` | **SMOKE FAIL** | 430 s | 400.2 s | **0/2** | 0.93 |
| `FASTDDS_BUILTIN_TRANSPORTS=UDPv4` | SMOKE PASS | 275 s | 242.4 s | 2/2 | 0.88 |

The 274 s include ~20 s of bring-up before the clock advances, so the steady
state is **RTF ≈ 0.95**. There is nothing left to win here: the co-simulation
already runs at real time on this machine, emulation included.

## The two "demo pace" knobs do not deliver

The roadmap that predates 2026-07-26 carried a *Demo pace* workstream proposing
both of these — the current one no longer does. They were measured anyway,
because they are the two knobs anyone reaches for first. Neither survives.

**Comm step `0.01` → `0.02` buys 4.7 %, not the 25 % expected**, and that is
inside run-to-run noise for a trajectory the reference itself calls
non-reproducible. The reason is already in this repo's cost model:
`ms/trip ≈ 1.3 + 2.4 × substeps`. Doubling the communication step halves the
number of round trips but doubles the substeps inside each one — the substep
total is unchanged, and only the 1.3 ms of transport is saved. *The cost is in
the substep, not the transport.* Rejected: 5 % does not pay for moving toward
the step size where yaw oscillation appeared.

**Wind `3.0` → `4.5 m/s` breaks the navigation.** The gate fails 0/2 with the
boat 100 m off the course area — last position `(-59.6, -91.5)` for a course
that lives between `(0,0)` and `(0,15)`. More wind is not a speed knob: the
reference pilot's rounding logic is calibrated for 3 m/s, and re-tuning it is a
piece of work, not a setting. Rejected until the pilot is re-calibrated.

## Where the time actually goes: rendering

| condition | RTF |
|---|---|
| headless | **0.93** |
| Unity player, 640×360 window | 0.75 |
| Unity player, fullscreen | 0.64 |
| Unity player, default window | 0.56 |
| any of the above while the machine is swapping | 0.04 – 0.12 |

Attaching the renderer costs **~40 % of the clock**, and the cost scales with
pixels. This dominates every simulation-side knob by an order of magnitude.

The mechanism is not raw CPU share: the player takes ~0.9 core out of 8 and the
machine is nowhere near saturated. The chain is **latency-bound, not
throughput-bound** — every communication step is a blocking gz↔xdyn round trip,
so work inserted into gz's loop (serialising poses, pushing them over TCP through
an emulated Python endpoint) is paid directly in RTF. Why a 0.9-core player costs
that much on a multi-core machine is **not established**; scheduling of
Rosetta-translated threads onto efficiency cores is a plausible but unmeasured
explanation.

`FASTDDS_BUILTIN_TRANSPORTS` is not part of this: forcing UDP-only measures
identical to the default. The DDS traffic is a 30 Hz command plus pose
publications, and the physics loop is a localhost websocket that never touches
DDS.

## Consequences

- **The Mac is a gate machine, and a demo machine only at reduced resolution.**
  Headless it reproduces the reference numbers exactly; with a renderer attached
  it is 1.8× slower than a native x86-64 desktop, which is what makes the same
  boat look sluggish next to the Windows setup.
- **Watch the swap.** 4.6 GB of swap on this 16 GB machine took RTF to 0.04. The
  Docker VM claims 7.7 GB for a stack that uses under 1 GB; lowering it is the
  cheapest recovery, and it is a Docker Desktop setting, not a repository one.
- **The real fix is native arm64 xdyn** (ROADMAP workstream 3), because it is
  xdyn — ~0.9 core under emulation — that leaves no headroom for the renderer.
