# Measurements — native Ubuntu 24.04 (WSL2), 2026-07-25

Answers to the open questions of `docs/design/2026-07-25-multiplatform-design.md`,
measured on the reference platform rather than argued.

**Machine:** AMD Ryzen 7 5800X (8C/16T), Ubuntu 24.04 under WSL2, ROS 2 Jazzy,
Gazebo Harmonic 8.14, core at `LOTUSim@regatta-base`, `physics/xdyn-for-cs`
x86-64 running natively (no Docker, no emulation).

## Q1 — does xdyn merge or reject two `environment models:` sections?

**Neither: the last file replaces the section wholesale.** Sections are not
merged element-wise, and a duplicate is not an error.

```bash
$ cat /tmp/wind_only.yaml
environment models:
  - model: uniform wind
    velocity:  {unit: m/s, value: 3.0}
    direction: {unit: deg, value: 180.0}

$ cd "$LOTUSIM_PATH/assets/models"
$ LD_LIBRARY_PATH="$LOTUSIM_PATH/physics" "$LOTUSIM_PATH/physics/xdyn-for-cs" \
    focus_v2/focus_v2.yaml /tmp/wind_only.yaml -s rk4 --dt 0.005 -a 127.0.0.1 -p 12399
The input you provided is invalid & we cannot simulate. Force model
'non-linear hydrostatic (fast)' needs a wave model, even if it's 'no waves'
```

The core model's `no waves` entry disappeared with the rest of its section — proof
of replacement rather than concatenation (which would have kept it) or of rejection
(which would have named a duplicate).

With the **complete** section in the second file (`no waves` + `uniform wind`), xdyn
starts and the layered wind is what drives the dynamics — 200 steps from the same
initial state, core alone (wind 90°) against core + conditions (wind 180°):

```
core only      (wind 90) : x=0.2728 y=0.5421 u=0.5223 v=0.0027
core + cond   (wind 180) : x=0.1543 y=0.4708 u=0.3472 v=0.0508
```

**Consequence:** the wind can leave the core model, but the scenario conditions file
must restate the whole `environment models:` section, not just the part it changes.

## Q3 — native performance

The design expected native x86-64 at RTF 3–4 against Rosetta's ≈ 1.0. **It is not:
one rk4 substep costs ≈ 2.4 ms here against ≈ 3.1 ms under Rosetta — a 1.3× speed-up,
not 3–4×.**

Round-trip cost against the number of internal substeps per communication step
(400 steps each, offline websocket path, no gz):

| xdyn `--dt` | comm step | substeps/trip | ms/trip | ms/substep | RTF |
|---|---|---|---|---|---|
| 0.005 | 0.005 | 1 | 3.71 | 3.71 | 1.35 |
| 0.005 | 0.01 | 2 | 6.55 | 3.27 | 1.53 |
| 0.001 | 0.005 | 5 | 12.70 | 2.54 | 0.39 |
| 0.0005 | 0.005 | 10 | 24.33 | 2.43 | 0.21 |

The fit is `ms/trip ≈ 1.3 + 2.4 × substeps`: a fixed ≈ 1.3 ms of websocket round trip,
then the integration itself. **The cost is in the substep, not in the transport** —
so the co-sim protocol is not the bottleneck and there is nothing to win by batching
communication.

**Consequences:**

- The harness config (comm 0.01, `--dt 0.005`) runs at RTF ≈ 1.5 offline, against
  ≈ 1.01 under Rosetta. Wall-clock and simulated time stay close enough that the old
  smoke gate would not have produced *wrong* verdicts here — but it stops being an
  accident that must hold, which is exactly why the gate moves to simulated time.
- The offline oracle's own config (`--dt 0.001`, comm 0.005) is the slow corner of
  the table at RTF 0.39: a 161 s lap costs ≈ 7 min wall. That is the price of the
  fine integration step the oracle uses on purpose, not a platform problem.
