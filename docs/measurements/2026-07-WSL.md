# Measurements — native Ubuntu 24.04 (WSL2), 2026-07-25

Answers to the open questions of `docs/design/2026-07-25-multiplatform-design.md`,
measured on the reference platform rather than argued.

**Machine:** AMD Ryzen 7 5800X (8C/16T), Ubuntu 24.04 under WSL2, ROS 2 Jazzy,
Gazebo Harmonic 8.14, core at `LOTUSim@regatta-base`, `physics/xdyn-for-cs`
x86-64 running natively (no Docker, no emulation).

## Q1 — does xdyn merge or reject two `environment models:` sections?

**Neither: the last file replaces the section wholesale.** Sections are not
merged element-wise, and a duplicate is not an error.

```bash
$ cat /tmp/wind_only.yaml
environment models:
  - model: uniform wind
    velocity:  {unit: m/s, value: 3.0}
    direction: {unit: deg, value: 180.0}

$ cd "$LOTUSIM_PATH/assets/models"
$ LD_LIBRARY_PATH="$LOTUSIM_PATH/physics" "$LOTUSIM_PATH/physics/xdyn-for-cs" \
    focus_v2/focus_v2.yaml /tmp/wind_only.yaml -s rk4 --dt 0.005 -a 127.0.0.1 -p 12399
The input you provided is invalid & we cannot simulate. Force model
'non-linear hydrostatic (fast)' needs a wave model, even if it's 'no waves'
```

The core model's `no waves` entry disappeared with the rest of its section — proof
of replacement rather than concatenation (which would have kept it) or of rejection
(which would have named a duplicate).

With the **complete** section in the second file (`no waves` + `uniform wind`), xdyn
starts and the layered wind is what drives the dynamics — 200 steps from the same
initial state, core alone (wind 90°) against core + conditions (wind 180°):

```
core only      (wind 90) : x=0.2728 y=0.5421 u=0.5223 v=0.0027
core + cond   (wind 180) : x=0.1543 y=0.4708 u=0.3472 v=0.0508
```

**Consequence:** the wind can leave the core model, but the scenario conditions file
must restate the whole `environment models:` section, not just the part it changes.

## Q2 — does the gz path need the patched initial state?

**No.** The hypothesis holds: `regatta.world` spawns the boat at ENU yaw 0.5236 rad
(NED heading 60°, close-hauled on starboard) and the physics plugin seeds xdyn from
that gz pose, so the `psi` and `u` the harness used to patch into the core model
never governed this path.

Run with the **unpatched** core model, wind from the scenario conditions file:

```
pose msgs seen: 8494 | sim t: 172.4s | last pos: (-0.225, 1.637)
windward: closest 1.46 m (need < 1.8)
leeward: closest 1.65 m (need < 1.8)
SMOKE PASS
```

The lap completes in **172 s of simulated time**, against 160 s for the offline
oracle, which starts with way on (`u = 0.8`). Starting from rest costs about twelve
simulated seconds — the boat bears away and accelerates on its own because the world
gives it a sailing angle, not because the model YAML seeded a speed. Being in irons
was always a heading problem, and the heading comes from gz.

The patch is therefore removed from the gz path. `offline/ws.py` keeps its own
seeding: the oracle has no gz to place the boat, and it sweeps the wind as a
parameter on purpose.

## Acceptance run, and one thing to watch

First run, from a clean interactive **bash** login shell, when `install.sh` still
appended its exports to `~/.bashrc`:

```
$ ./scripts/run_regatta.sh 600 smoke
pose msgs seen: 8488 | sim t: 172.3s | last pos: (-0.232, 1.745)
windward: closest 1.46 m (need < 1.8)
leeward: closest 1.76 m (need < 1.8)
SMOKE PASS                                    exit=0, 3 min 08 s wall
```

That mechanism was then dropped: writing to `~/.bashrc` serves only bash users, and
it is not ours to write into. The criterion became stricter — a **bare zsh shell**,
nothing sourced by hand, no rc file involved, the harness setting up its own
environment:

```
$ zsh -c './scripts/run_regatta.sh 300 smoke'
pose msgs seen: 8492 | sim t: 172.4s | last pos: (-0.229, 1.708)
windward: closest 1.46 m (need < 1.8)
leeward: closest 1.72 m (need < 1.8)
SMOKE PASS                                    exit=0
```

**The leeward rounding passes by 4 cm.** Two runs of the same commit gave 1.65 m and
1.76 m against a 1.8 m threshold, so the trajectory is not bit-reproducible — the
helmsman ticks on a 30 Hz wall-clock ROS timer while the physics advances on the sim
clock, and the two do not lock. The gate is therefore one bad run away from a false
FAIL, and no code change would be to blame. Worth fixing at the source (drive the
helmsman off the pose stream rather than a timer) rather than by widening `WP_R`,
which would only hide it.

## A gate that passed for the wrong reason

Worth recording, because it cost an hour and would cost it again. The first native
`SMOKE PASS` came back in **17 simulated seconds** for a lap that takes 170. The
cause was not physics: a gz orphaned by an earlier run was still publishing on
`/world/lotusim/dynamic_pose/info`, so the pose stream carried two boats — one
parked near each mark — and the gate counted both marks at once.

It was visible in the pose stream as consecutive samples 14.6 m apart, which no
0.01 s step can produce. The fix is in `scripts/regatta_stack.sh`: kill the process
tree rather than the wrapper PID, and refuse to start when something already
publishes on the world's topics.

## Q3 — native performance

The design expected native x86-64 at RTF 3–4 against Rosetta's ≈ 1.0. **It is not:
one rk4 substep costs ≈ 2.4 ms here against ≈ 3.1 ms under Rosetta — a 1.3× speed-up,
not 3–4×.**

Round-trip cost against the number of internal substeps per communication step
(400 steps each, offline websocket path, no gz):

| xdyn `--dt` | comm step | substeps/trip | ms/trip | ms/substep | RTF |
|---|---|---|---|---|---|
| 0.005 | 0.005 | 1 | 3.71 | 3.71 | 1.35 |
| 0.005 | 0.01 | 2 | 6.55 | 3.27 | 1.53 |
| 0.001 | 0.005 | 5 | 12.70 | 2.54 | 0.39 |
| 0.0005 | 0.005 | 10 | 24.33 | 2.43 | 0.21 |

The fit is `ms/trip ≈ 1.3 + 2.4 × substeps`: a fixed ≈ 1.3 ms of websocket round trip,
then the integration itself. **The cost is in the substep, not in the transport** —
so the co-sim protocol is not the bottleneck and there is nothing to win by batching
communication.

**On the gz path itself — the one that matters — RTF is ≈ 1.0**, measured from the
pose stream during a real lap (simulated time advanced 32.0 s in 32.0 s of wall
time, boat speed 0.36 m/s). That is the same figure Rosetta gave. The design's
"native x86-64 is expected at RTF 3-4" does not hold on this machine.

An earlier reading of RTF 4.5 was an artifact: a leftover gz from a previous run was
still publishing on the same topics, and its older clock was what got sampled. See
the note on the smoke gate below.

**Consequences:**

- The harness config (comm 0.01, `--dt 0.005`) runs at RTF ≈ 1.5 offline and ≈ 1.0
  through gz, against ≈ 1.01 under Rosetta. So the old wall-clock gate would not have
  produced *wrong* verdicts here — but it only ever worked by coincidence, and the
  coincidence is now known to be machine-dependent rather than reliable.
- The offline oracle's own config (`--dt 0.001`, comm 0.005) is the slow corner of
  the table at RTF 0.39: a 161 s lap costs ≈ 7 min wall. That is the price of the
  fine integration step the oracle uses on purpose, not a platform problem.
